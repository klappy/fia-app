# Executable publications are a content-keyed cache (Mark 1:14–20 opens on DEV again)

Server: the executable publication store is a content-keyed cache, never an identity or trust ledger (cookbook ruling "DEV publication conflict", 2026-10-17). A publish whose record key already exists now replaces the row and advances the pointer, so re-preparing byte-identical bytes under a moved execution policy (DEV's `{9a7733f5, @2}` rows after #249) opens the passage executable instead of answering `blocked` `executable-publication-conflict` (HTTP 409). That code no longer exists, and no adoption ledger is added (supersedes draft #251).

A stored row that fails byte, hash, length, binding, eligibility or validation checks, or a dangling or foreign pointer, is a cache miss: the catalog read falls through to the base record (with its existing preparation demand, so an explicit Open re-prepares) and the artifact read falls through to the base artifacts. It never answers `unavailable` because of the stored row. Each miss, and each replacement of a different row, is signalled through a `diagnostics` hook that the Worker logs (`executable-cache-miss`, `executable-cache-replace`) for bookkeeping only. Integrity pins stay for diagnostics and refresh, not as a usage gate. Client, content and catalog bytes are unchanged.
