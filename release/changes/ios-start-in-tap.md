# iOS: later screens start on one tap-unlocked audio element; a silent start ends as Resume

On DEV the captain's iPhone showed the starting spinner forever on every screen after the first. Each clip played on a new audio element, and every start after the first tap came from a media or timer callback, never from a tap. iOS lets an element start without a tap only once a tap has started that same element, and until then loads nothing for it, so a later screen's start neither played nor failed. The starting face added with the easy button (RECIPE R4) waits for sound with no bound, and a tap on it is absorbed, so nothing ended the spinner. Production has no starting face: a stalled start fell to Resume, and that tap started the clip.

Every clip now plays on one audio element, its source swapped per clip. The first tap anywhere in the app starts that element and at once pauses it while it is idle, so later screens may start on it without a tap; a tap never touches an element that holds a clip. A start with no sound 1.5 s after the clip is handed to the player (`START_BOUND_MS`, re-armed when the player calls `play()`) is paused and reported through the existing autoplay notice, keeping the verified bytes: the centre shows Resume with "Tap Play to hear the narration. Your browser paused automatic audio." and one tap starts the clip inside the tap. A start superseded by a pause, a stop or the bound no longer reports. Resume of a clip whose media never loaded starts the element inside the tap, then the range seeks and plays. One tap still plays, the checking pulse is unchanged, and a Continue tapped while checking is still dropped (E4).

Not changed: video starts have no bound; media loading and preparation keep their own bounds (the service worker's 10 s and 45 s, preparation polling). The first tap anywhere starts and pauses the idle element once, which on iOS may pause other audio the person is playing. WebKit is not installed where the checks run, so the iOS rules are emulated in Chromium; DEV needs a check on a real iPhone after deploy.

Validation: `e2e/fixtures/ios-playback.js` emulates the iOS rules in Chromium (an audio element with sound starts only inside a tap's window or once a tap has started it, loads nothing until then, and a start it does not allow stays pending or is refused), using trusted input only. `e2e/ios-playback.spec.js` on Mark 1:1–13: one tap on Begin, then screens 2 and 3 start on their own with no spinner past the bound; and under the strictest gate, a pending start ends as Resume with its notice at the bound, one tap plays it and later screens start on their own. Against the build before this change both fail: screen 2 spins for over 60 s after its clip is handed over while screen 1 plays, as on the captain's iPhone, and under the strict gate screen 1 spins past 10 s. Unit tests cover the bound (a pending range, a range that never loads, a pending whole file, a refusal reported once, a pause or stop before the bound, sound inside the bound), one element across clips and the unlock. An App-boundary test checks that the starting face ends as Resume with its notice and one tap resumes. Harnesses that counted constructed elements now count clips loaded into the one element.
