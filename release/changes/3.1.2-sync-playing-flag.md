# 3.1.2: `sync()` reports whether the clip is really playing

Version `3.1.2` is 3.1.1 plus one change in the audio controller, `apps/web/src/lib/audio.js`: when the page becomes visible again, `sync()` recomputes the playing flag from the media element before it sends its state report. No content pack, server, service worker, audio-master planner, script controller or page file changes: nothing under `apps/web/public/content` or `server/`, and not `apps/web/public/sw.js`, `apps/web/src/lib/continuous-reading.js`, `apps/web/src/lib/script-controller.js` or `apps/web/src/App.svelte`.

## Why

The controller keeps a flag that it sends as `playing` in every state report. It recomputes the flag in `update()`, which runs on the element's `timeupdate`, `playing` and `ratechange` events, and it has no `pause` handler. `sync()`, which the page calls on `visibilitychange` and `pageshow`, re-armed the range boundary and sent a report without recomputing the flag. If the browser or the operating system paused the element while the page was hidden and delivered none of those events afterwards, the page came back reporting playing: the main button read Pause and the screen wake lock was taken again, although nothing played. Two taps recovered.

The defect was found by reading code (an automated code review comment on pull request 373 and the traced reply under it). It has not been observed on any phone or in any browser.

## What changes

`sync()` gains one line before the boundary line: the flag is set from the same three terms `update()` uses, namely that the clip has reached sound, that the controller has not paused it, and that the element is not paused. Its comment gains one sentence. After an outside pause the report now carries `playing` false, the main button reads Resume, the page releases the wake lock, and one tap reaches `resume()`, which calls `play()` on the same element inside the tap. Nothing else in the controller changes: no `pause` handler is added, and `update()`, `state()`, `seek()`, `resume()`, `pause()` and the boundary functions are unchanged.

Four test cases cover it. In `apps/web/tests/audio.test.js`: an outside pause with no event, then `sync()` and one `resume()`; `sync()` while the clip plays; `sync()` during a first start that has not reached sound. In `apps/web/tests/audio-range.test.js`: an outside pause of a ranged clip, one `resume()`, and the range still ending once.

## Not fixed, not shown

- The defect on any phone or in any browser, and sound after one tap on a phone.
- A stale flag with no visibility change: if the element is paused from outside while the page stays visible and no event arrives, nothing calls `sync()`. `seek()` also reports without recomputing the flag and is not changed.
- The wake lock on hardware. No test names the wake lock.
- A `sync()` while a `play()` made by `resume()` is still pending reports playing and cancels the start bound, as `update()` already does on any `timeupdate`; this release does not change that.
