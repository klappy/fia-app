# Truthful passage switch (R1)

Repairs red DEV (`3d3b1d2`): opening Mark 1:14–20 showed "The server catalog is invalid.", a saved refused passage showed that toast on every launch, and returning to Mark 1:1–13 failed with a 500.

The service worker now passes the server's answer for `/v1/packs` and `/v1/artifacts` to the page unchanged: status, content type and JSON body. It no longer rewrites a non-200 into a plain-text 409. Verification still decides whether a saved snapshot stays usable. Only a failed fetch or a transient server status may use a verified saved snapshot. "The server catalog is invalid." is now reserved for a malformed record.

The Passages sheet shows the truth next to the card that was opened. Open is disabled and `aria-busy` while its request is pending. An unavailable or refused passage keeps the sheet open, says so in the card, stops claiming recordings on request, and leaves the current passage, its playback and its saved progress unchanged. The reading screen gets a notice only if the sheet was closed before the answer arrived. A saved passage that cannot be restored at launch leaves the default passage open with one short notice and clears the saved key, so later launches are quiet. A missing connection keeps the key: no answer or a transient status, for the passage record or for its presentation artifact, is a missing connection, and the notice says the saved passage could not be reached.

Server: a publication validated under the one registered superseded execution policy (the build before PR #189 added the approved-audio proof index to the policy hash) no longer shadows its base record. Only after the unqualified current read authenticates that historical publication exactly (pointer, owner indexes, closed rows, recomputed job id, retained bytes, request binding, reproduction under the historical policy) does it serve the base with its existing four-field preparation demand, so an explicit Open prepares under the current policy. A reason string alone, or a forged, unregistered or corrupt row, a wrong pointer or missing bytes, stays refused, and the read writes nothing. The historical revision and its old job status stay denied. Publication rows are never overwritten: republishing identical bytes under a newer job answers `blocked` `executable-publication-conflict`. Expected publication conflicts, named post-admission refusals and a stale-policy job-status read answer typed `blocked` with their code (HTTP 409); an unnamed fault is not disguised as one. The approved original Mark 1:1–13 presentation is no longer offered, or admitted for, a preparation it cannot fulfil. Any resolver or projector refusal is a typed `blocked` answer with its code (HTTP 409), never a 500; a transient storage or fetch fault during resolution answers the same way, writes no job row and can be retried. The four-field demand is the interim for this tree, which has no publication generations: cookbook backport klappy/fia-app-cookbook#223.
