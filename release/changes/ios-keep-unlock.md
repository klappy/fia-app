# iOS: a finished clip no longer empties the one audio element

Review of the iOS start fix (Bugbot on #205) found that releasing a clip still emptied the shared element's source and called `load()`: the teardown from when each clip had its own element. On WebKit that empty load may return the element to locked, so a later screen's untapped start would hang again until the 1.5 s bound turned it into Resume. Releasing a clip now only pauses the element; the next clip's source swap reloads it, and the previous clip's late events stay ignored by the generation check. That swap also resets the playhead and queues a timeupdate inside the new clip, after `play()` has cleared `paused` but before any sound, so a clip now counts as playing only once it has reached sound (its own `playing` event or a resolved `play()`), never on a timeupdate alone; otherwise that event would end the start bound on a silent start. A replay of the same source (a downloaded clip plays by its path) sets the same value again; the spec and Chromium reload on that, and the controller also returns a whole-file replay to the start, in case a browser does not.

Not changed: the start bound, the unlock on the first tap, and range seeking. A released element keeps its last source until the next clip replaces it. Whether WebKit relocks on an empty load is not measured on a device; the iOS emulation now takes the stricter reading.

Validation: `e2e/fixtures/ios-playback.js` gains `loadResets` (default on): a `load()` on an audio element left with no source returns it to locked. With it, both `e2e/ios-playback.spec.js` tests fail against the build before this change (screens 2 and 3 never start after one tap) and pass with it. A unit test plays a clip to its end, then a second clip whose start stays pending, and fires the reset timeupdate: before the sound rule the controller reported playing and the bound was gone; now the bound hands it back as Resume. Another plays a downloaded clip, moves the playhead and replays the same source: it starts from 0 (failed before the reset). Two unit tests that checked the emptied source now check that the element is paused, keeps its source and is never emptied with `load()`, and that the controller is released.

Not covered: a released element still holds its last clip, so a lock-screen or headset play control could restart it while the controller shows nothing playing; the app sets no media session handlers.
