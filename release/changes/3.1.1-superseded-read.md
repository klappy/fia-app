# 3.1.1: Spanish Luke honest text with the superseded-read answer

Version `3.1.1` is 3.0.3 (with PR372, the passage-timing `clamped` tier, merged on `main` under that label) plus two changes that must travel together. The Spanish Luke honest-text recompile (PR356) returns to `main` by reverting its revert (`5fd88de`); its own note is [2026-11-09-spanish-luke-honest-text.md](2026-11-09-spanish-luke-honest-text.md). And the server changes the HTTP status of one kind of answer, described here. This release does not change `apps/web/public/sw.js`. The worker it ships is the 3.0.2 worker (blob `478db8d6`), which differs from the 3.0.1 worker (blob `deb8b943`) only in line 339, the `/welcome` pass-through entry from PR322. The test fixture `apps/web/tests/fixtures/sw-3.0.1.js` stays blob `deb8b943`.

## Why

The recompile replaces the published revision of 262 of 330 passages. A device that saved a passage keeps reading it by the revision it saved. A server that no longer holds that revision answered such a read with HTTP 404 `revision-not-found`, and the service worker already installed on devices treats a 404 as a withdrawal: it revokes the saved copy, and the passage is blank offline (defect D1). The same worker treats 408, 429, 500, 502, 503 and 504 as "the server could not answer" and keeps the saved copy. PR360 did not change this.

## What changes

One function, `serveRead` in `server/faces/http.mjs`:

| Read | Result | Before | Now |
|---|---|---|---|
| Passage pinned to a revision this build does not hold | `unavailable`, `revision-not-found` | 404 | **503** |
| Passage that does not exist, read pinned | `unavailable`, `revision-not-found` | 404 | **503** |
| Artifact digest this build does not hold, or whose static file is missing | `unavailable`, `not-found` or `artifact-not-found` | 404 | **503** |
| Unknown passage, read without a revision | `unavailable`, `not-found` | 404 | 404 |
| Artifact that fails its integrity check | `unavailable`, `artifact-integrity-failed` | 404 | 404 |
| Refused, blocked, preparing, ready | | 400, 409, 202, 200 | unchanged |
| Preparation routes (`/v1/presentation-preparations`) | | | unchanged |

The JSON body is the same as before, byte for byte, with `Cache-Control: no-store`. The MCP face returns typed bodies without an HTTP status and is unchanged.

A read pinned to a prepared record that is corrupt or revoked falls to the base's `revision-not-found` and so also answers 503. That is a behavior change: before this release it answered 404 and an installed worker dropped the copy.

## What a device sees

A saved passage stays saved and opens offline after the server moves to new text. The device keeps the old text until the person updates the download while online; the Downloads sheet says a newer download is available. While the old passage is still on screen online, saving it again ends with "temporarily unavailable" wording and its media check can fail until a reload.

A saved passage whose copy was made from a prepared record (the usual case when the passage was opened from the Passages sheet before it was saved) is not replaced by a plain tap on "Update download" after this release. The installed service worker refuses the tap with "The executable saved passage is preserved. Reload before saving this selection." and keeps the saved copy, which stays usable offline with its earlier text. A reload by itself does not clear the refusal. The guard is the installed worker's own, unchanged since 3.0.0. People meet it now because this release keeps saved copies instead of revoking them, and every copy prepared on an earlier version needs a fresh preparation on this one, including passages whose text did not change.

To get the new text into a saved passage, while online:

1. If the app was open while the version changed, close it and open it again.
2. Tap the passage name at the top to open the Passages sheet. On the card of the same passage tap "Open passage" (the button reads "Resume passage" once the passage has been started), even though that passage is already on screen. Do not tap "Restart passage": it clears the passage's saved progress. Wait until the passage has opened.
3. Tap the FIA mark ("More options"), then "Downloads".
4. Choose the option the copy was saved with. The sheet starts on "Text only".
5. Tap "Update download" and wait for "The download is verified."
6. Tap "Reload saved version".

These steps were seen to work in desktop Chromium on local builds, not on a phone.

On a "Text and audio" copy the Downloads sheet preselects "Text only", so choose "Text and audio" again before "Update download", or the saved recording is dropped. This was already so before this release.

## What it costs

- The status says "temporary" for something permanent.
- Removing a revision no longer withdraws saved copies, and no pinned pack read answers 404 any more, so the server can no longer withdraw one revision of a passage that stays published until a later change adds an explicit way. Dropping a passage from a build, or a pinned read answered 200 with a different revision, still makes the installed worker revoke the copy, so a future build must not drop or rename a published passage by accident.
- Once this build has served an environment, that environment is not rolled back to an earlier build: the earlier build answers 404 to copies saved under the newer revisions. See "Superseded reads" in `RELEASING.md`.
- The 503 reaches reads that are not superseded reads. A read pinned to any revision of a passage id that does not exist, a read of any well-formed artifact digest this build does not hold, and a read of an artifact the build lists but whose static file is missing all answer 503 where they answered 404. The last one is a deploy or data fault: the status now says "temporary", the page tells the reader to check the connection, and the post-deploy journey fails on it only for the passages that journey opens.

## Tests

- `tests/worker-serving/superseded-read.test.mjs`: the table above through the real `serveRead` over the packaged snapshot, and through the deployed adapter.
- `apps/web/tests/saved-pack-superseded-read.test.js`: a saved copy, a server that moves on, and seven ways a read naming the old revision reaches the server, for the worker frozen from 3.0.1 (`apps/web/tests/fixtures/sw-3.0.1.js`) and the current worker. A 503 keeps the copy in every case; a 404 revokes it in every case that sends a pinned read. One case takes the stale answer from the real server code.
- `apps/web/tests/helpers/offline-execution.js` gains an option so the fake server answers a superseded read like the real one. Without the option it still ignores the revision parameter, which is how the PR360 regression test passed against a server that does not exist.
- Existing assertions that expected 404 for these reads now expect 503.

## Limits

Not shown: a phone, iOS Safari or an installed home-screen app; whether the hosting edge passes the server's own 503 through unchanged (checked on staging after the deploy, not locally); workers older than 3.0.0. Copies already revoked on test devices are not restored. Each environment still requires independent review, required checks and exact-commit post-deploy evidence under `RELEASING.md`. This note does not merge or deploy anything.
