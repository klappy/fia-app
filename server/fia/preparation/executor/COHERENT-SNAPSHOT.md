# Post-observation coherent snapshots

This coordinator implements the served/desired portion of cookbook PR174, `SOURCE-FRESHNESS-RECIPE.md` SHA `2b3f10bd66638187e8921bd3e5a9f41a71696d9f05888bd0c2843ec0c419e436`. Source base is reviewed `9dc75488f9516ea8eb8533e1391b03718884b395`, retaining its known-original limits. It does not perform the separately authorized fresh-byte observation, source fetching, acquisition, ASR, public admission, or app playback adoption. Existing publication, pipelines, 2 MiB storage, routes, release files and hosted activation are unchanged.

`createCoherentSnapshots({storage,bucket,policy:{sha256,validateSnapshot},builder:{paid:false,run},eligibility,totalMs?,progressMs?})` exposes `demand(observation,{signal?})` and `read(logicalId)`. These are private trusted composition ports. SQLite transaction storage and content-addressed R2 object access are required. Callback/function references and policy hash are captured when constructed; request values are cloned before awaits. No paid builder is admitted. The production builder and semantic/clock acceptance validator are not implemented by this increment.

An observation contains `logicalId`, a trusted positive monotonic `sequence`, `expectedPreviousObservationSha256` (null only for the first head), provenance `{checkId,sourceVersionKind,sourceVersion,publisherVersion,observedAt}`, and dependency identity. Version kinds remain `discovery-snapshot`, `publisher-version`, or `observed-content`; the latter must equal the source SHA, and a publisher-version label must match its separately supplied publisher version. Unknown publisher version remains null. This metadata is trusted upstream evidence, not a freshness check performed by the coordinator.

Dependency identity has six actual SHA-256 values: source, script, recognition configuration, alignment configuration, delivery configuration, and acceptance policy. The acceptance policy hash must equal the factory's captured policy pin. Observation/check/time/version provenance is excluded from dependency identity. Re-observing identical dependencies updates the observation head without rebuilding. Observation admission uses both monotonic sequence and expected-head CAS, so a delayed older demand cannot replace the desired head. Identical admitted demand and pending builds share one durable refresh. Changed identity claims only the requested replacement; no descendant sweep or scheduler is created.

Candidate manifests use schema `fia-coherent-snapshot@1`, logicalId, exact dependency identity and a fixed artifact graph. Every artifact descriptor has SHA, exact byte size, content-addressed reference and a parent role-to-SHA map:

- Roots: source, script, recognitionConfig, alignmentConfig, deliveryConfig, acceptancePolicy.
- Recognition depends on source and recognitionConfig.
- Alignment depends on recognition, script and alignmentConfig.
- Delivery depends on source and deliveryConfig; recognition/text changes do not inherently replace it.
- Timing depends on alignment and the actual delivery clock.
- Acceptance depends on source, script, recognition, alignment, timing, delivery and acceptancePolicy.
- Presentation depends on script, delivery, timing and acceptance.

All retained objects are streamed and rehashed before promotion and each served read. Exact root hashes and all edge joins must match. Recognition, alignment, timing and presentation JSON must embed exactly their manifest parent map. Acceptance bytes must contain schema `fia-snapshot-acceptance@1`, an independently accepted status, exact identity and only its parent set; it does not circularly hash itself or the later presentation. `policy.validateSnapshot` receives the full verified manifest, retained non-media bytes and parsed acceptance. It must independently validate the domain's actual structured evidence, semantic/rights/clock requirements and presentation binding and return synchronous strict `true`. Accepted text inside an artifact alone is insufficient. Promises, truthy substitutes or exceptions refuse promotion. Fixture policies are not production acceptance policies.

Promotion rechecks the latest desired revision and synchronous local `eligibility` decision inside the same transaction that updates the served head. Eligibility must consult current trusted rights/known-bad state without an asynchronous gap. Read rechecks eligibility after all retained verification. Revocation or bad bytes refuse serving. A newer provenance observation for the same dependency revision can adopt shared work; a different desired revision cannot be replaced by a stale completion. A previously completed revision can be reverified and promoted again if it becomes the current desired revision. Returning a whole served snapshot does not silently swap an active client playback clock; session-boundary adoption remains outside this module.

Refresh failures, blocked review, or an uncertain/timed-out builder retain the previous eligible coherent snapshot. There is no automatic retry or reconciliation of uncertain refreshes. Stored observation head, desired refresh state and served manifest remain separate. A policy-pin change deliberately makes older-policy snapshots unavailable in this first slice: version-aware historical policy dispatch is not implemented. Source/config/text changes under the same acceptance policy can retain the old complete snapshot while replacement fails.

Bounds: manifest 32 KiB; source and delivery at most 8 MiB each; other artifacts at most 256 KiB each; declared total at most 20 MiB; stream input chunks at most 1 MiB. Non-media metadata is bounded and retained for semantic validation. Defaults are 120 seconds per refresh/verification phase and 15 seconds without stream progress. Demand may additionally revalidate the served snapshot with its own 120-second phase (at most two phase budgets); read has one phase. Test bounds only tighten limits. Cancellation/timeout does not wait on an unresponsive stream cancellation or imply a builder stopped; late builder artifacts cannot promote through the expired operation. Platform buffers and trusted synchronous callback CPU cost are not measured here. This is not a decoder-memory or hosted-runtime enforcement claim.

Run `node --test tests/preparation-executor/coherent-snapshot*.test.mjs`, with `FIA_WORKER_DEPENDENCIES` pointing to the existing installed Worker dependency package for SQLite/R2 tests. Tests cover eligible retention, policy/rights refusal, corrupt/transplanted state, missing/corrupt or mismatched dependencies, same-dependency observation deduplication, stale observation and late-promotion fencing, revision return, deadline/cancellation, and SQLite/R2 restart. Synthetic graph hash tests demonstrate intended dependency edges; they do not prove a production recognition adapter actually reuses nodes. Durable coalescing and immutable verification use actual local SQLite/R2; source/ASR/builders and clock semantics remain fixtures. No live objects, provider requests or infrastructure are created.
