# Retained presentation guide-unit resolver

`createPresentationGuideUnitsResolver({metadataBytes, metadataSha256, registryBytes, registrySha256, readPresentation, presentationAliases?, totalMs?})` returns the asynchronous `resolveUnits(input)` port consumed by the existing alignment adapter. Inputs use the exact section identity returned by the guide discovery resolver. `readPresentation(descriptor, {signal})` is a trusted retained-byte port, not a caller-controlled URL or a media fetcher.

Canonical pack/pericope identity is joined directly between the pinned metadata and registry. Publisher passage text remains exact (including `6:1-6a` and `6:6b-13`); it is never mechanically converted into a canonical pack ID.

Metadata and registry bytes are copied before any asynchronous hash operation, including Node Buffers. The resolver verifies their hashes, registry pack/language/revision/path/length, entire presentation bytes, guide-content provenance, exact section, complete expected unit pins and each canonical UTF-8 text hash. Input and resolved bytes are captured before asynchronous work. Metadata/registry are bounded at 2 MiB each, presentation at 4 MiB, section units at 1,000, and section text at 200,000 characters. The retained-byte read has a maximum 30-second deadline and abort signal; cleanup never waits indefinitely.

Canonical activities must have `id === sourceUnitId` and use `sourceText` plus `sourceSha256`. Narration is never substituted. Generated resource activities are not canonical source units. Exact expected optional example units use their retained `id/text/sha256` and matching coverage treatment/hash; collisions with canonical activities refuse the entire section. Unit order comes from the hash-pinned metadata section manifest. An example's returned `activityId` is a logical source-unit binding for alignment, not a claim that the current renderer exposes a playable activity.

`scriptSha256` remains the existing discovery port's whole-guide `guideContentSha256`. That hash is a provenance assertion inside the verified presentation, not a claim that this resolver independently rehashed raw guide bytes. `sectionManifestSha256` separately hashes the ordered section unit manifest and all metadata/registry/presentation pins. Neither is silently substituted for the prepared-audio catalog's script identity. No source acquisition, ASR, alignment acceptance or playback range is produced here.

The default requires presentation body ID to equal the registry pack ID. Legacy body IDs require an explicit trusted alias with exact `{packId, presentationSha256, presentationId}`; no built-in P1 exception or heuristic exists. The tests pin the retained P1 legacy alias and refuse wrong revisions or duplicate aliases.

Required Worker CI imports the focused suite. It uses hash-pinned metadata rows derived from the retained published metadata SHA `554e26f3d7cef0e4bb515923e4fcc081a29d407ef7291f122c6daf28205687a8`, and actual presentations/registry already in the repository. P2 S01, P2 S04 (including examples), P3 S01 and P1 S01 resolve. P1 S02 refuses because canonical U012 is absent; no source-pack fallback is invented. The wider audited corpus contains six missing canonical units across three P1 sections: S02 U012, S05 U044/U045, S06 U005/U007/U009. With the exact P1 alias, the parent audit found 405 of 408 complete sections; default strict body IDs exclude P1. These are text-join counts, not preparation or acceptance coverage.
